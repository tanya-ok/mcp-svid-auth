Fail-closed replay cache is a shared, unbounded-by-client DoS surface with no way to size it

unresolved

Codex challenge: needs test

The global capacity check and default cache allocation support contention between subjects using one server instance. However, changing jti requires a newly valid signature, and assertion issuance capabilities and throughput are outside the snapshot. The roughly 30 requests/second exhaustion scenario is therefore unproven. The claim that sizing requires code changes is too broad: ReplayCache accepts max_entries and AuthzServer accepts replay_cache, although the supplied CLI exposes neither. Validate exhaustion using realistically obtainable assertions and verify another subject's rejection. Per-sub caps reduce individual impact but do not guarantee availability when the global cap fills.

Claude response: needs test

The structural half of F1 is confirmed by the snapshot: one process-wide ReplayCache (authz.py:118) capped at 10_000 (authz.py:46), and a full cache returns temporarily_unavailable/503 to every subsequent assertion regardless of subject (authz.py:95-101), with entries held until exp + skew (authz.py:257). So availability is coupled across all allowlisted clients in reject mode. The exploitability claim is unproven. Filling the table needs ~10k distinct validly signed assertions, and the snapshot's own comment notes SVID sources that cache and re-serve a single SVID (authz.py:47-48), which in reject mode would be rejected as replay rather than adding entries; assertion minting rate lives in omitted spiffe_keys/SPIRE behaviour, so the ~30 requests/second figure is arithmetic, not a measured or source-supported capability. Also too broad: ReplayCache takes max_entries (authz.py:66) and AuthzServer takes replay_cache, so embedders can size it; only build_parser/main expose no flag. Test: fill the cache from one subject and assert a second subject still gets a token, using assertions obtainable from the real SVID source, before accepting priority 3. Note a per-sub cap limits one subject's share but does not restore availability once the global cap fills.

Kimi independent peer: needs test

The structural claim is confirmed: a single per-process ReplayCache (authz.py:118) capped at 10,000 (authz.py:46) returns 503 to all subjects when full (authz.py:95-101), with entries held until exp + _CLOCK_SKEW (authz.py:257), and no CLI flag exists to size it (authz.py:390-439, 453-461). However, exploitability is unproven: filling the cache requires ~10k distinct validly signed assertions, and the snapshot notes some SVID sources cache and re-serve one SVID (authz.py:47-48), which would be replay-rejected rather than adding entries. The claim that sizing requires code changes is overbroad since max_entries and replay_cache are constructor parameters. Test with real SVID source behavior before accepting priority 3.

Research claim and proposal

ReplayCache is a single process-wide table capped at DEFAULT_REPLAY_CACHE_SIZE = 10_000 (authz.py:46), and when it is full after evicting expired entries it raises temporarily_unavailable/503 for every further assertion (authz.py:95-101), as the docstring states (authz.py:63). Entries are only evicted once exp + _CLOCK_SKEW has passed (authz.py:257), so with the default max_svid_lifetime of 300s plus 30s skew a single allowlisted client that mints fresh jti values can pin ~10k live entries with roughly 30 requests/second and thereby deny token issuance to all other clients until its assertions age out. There is no per-sub or per-trust-domain bound, and build_parser (authz.py:390-439) exposes no flag for ReplayCache.max_entries, while main() (authz.py:453-461) never overrides the default, so an operator cannot raise or partition the limit without code changes. Replay protection itself is correct; the gap is blast radius and operability of the fail-closed path.

Bound the cache per subject instead of only globally, and make the limit configurable. Concretely: track a per-sub live count in ReplayCache.add and reject that sub once it exceeds a per-client cap, so one client's burst cannot exhaust capacity shared with others; keep the global cap as a backstop. Add a --replay-cache-size (and optional --replay-cache-per-client) CLI flag in build_parser and wire it through main() into ReplayCache(max_entries=...). Also emit the global-full condition as a distinct audit decision so operators can alert on it rather than inferring it from 503 counts, and document in the fail-closed docstring that capacity must be sized as max_svid_lifetime times the expected assertion rate.

FetchX509SVID stream never reconnects; one transient failure latches the bridge into permanent 503

consensus proposal

Codex challenge: support

Once run() rejects, its catch sets streamFailure and clears cachedSvid. getX509Svid() subsequently throws, and start() cannot restart because streamTask remains assigned. An unclosed clean stream end also rejects. The transport converts these request failures into 503 responses. This establishes the terminal state without runtime testing. However, agent restart and socket-drop behavior depend on the unavailable spiffe client implementation. The suggested cache retention and invalid-update skipping require separate security justification; they do not follow from the demonstrated reconnect defect.

Claude response: support

Supported on the mechanism, with scope caveats. start() returns early whenever streamTask is already assigned, and the single catch on run() sets streamFailure and nulls cachedSvid; no code path clears streamFailure, re-arms firstMessageDeferred, or reassigns streamTask. getX509Svid() therefore throws permanently once run() rejects, including after a clean stream end while not closed (line 123). The transport makes this user-visible: handleRequest's first statement awaits getX509Svid(), and the createServer wrapper converts the rejection into a 503. This is a latched-availability defect readable from the snapshot alone. Not established by the snapshot: that transient agent restarts or socket drops actually surface as rejections on call.responses (the spiffe client was not supplied), and that the suggested recovery semantics are correct. Retaining a cached SVID through a stream outage and treating an out-of-validity response as skippable are fail-open changes to credential handling; they need their own justification and should not be adopted as a side effect of fixing reconnect. Priority 3 is reasonable for an availability defect requiring process restart.

Kimi independent peer: support

The core latching defect is established from the snapshot: streamTask assignment at line 55 blocks restart via start()'s guard at line 54; the catch sets streamFailure and nulls cachedSvid with no clearing path; getX509Svid() throws permanently at line 66. Clean stream end at line 123 also rejects when not closed. Transport handleRequest awaits getX509Svid() first, converting to 503. However, the finding assumes without evidence that agent restarts and socket drops surface as rejections on call.responses (external spiffe client not supplied). The proposed cache-retention and invalid-response-skipping remedies are fail-open credential handling choices whose safety is unproven and should not ride along with the reconnect fix. The acceptance criterion presupposes these contested semantics.

Research claim and proposal

WorkloadApiSvidFetcher consumes the FetchX509SVID stream exactly once, with no retry or backoff. start() assigns streamTask = this.run().catch(...), and that single catch sets this.streamFailure and sets this.cachedSvid = null. run() also throws on a clean stream end (line 123) and on any response whose leaf is outside its validity window (line 111), so an agent restart, a socket drop, or one momentarily not-yet-valid SVID all land in the same terminal state. After that, getX509Svid() short-circuits at line 66 forever, because nothing clears streamFailure or re-arms streamTask or firstMessageDeferred. MtlsTransportServer.handleRequest awaits this.opts.fetcher.getX509Svid() as its first statement (line 134), so every subsequent request throws and is answered 503 by the createServer catch handler. A still-valid cached SVID is discarded rather than used for graceful degradation, so the process must be restarted to recover.

Make run() a supervised reconnect loop instead of a one-shot task: wrap its body in a while (!this.closed) loop that opens a fresh fetchX509SVID call each iteration, catches per-iteration errors, and sleeps with jittered exponential backoff (for example 100ms up to a 30s cap) before retrying. On each error set a transient field such as lastStreamError, used only to reject a still-pending firstMessageDeferred, then re-arm this.firstMessageDeferred = deferred() so later callers await the next connect instead of inheriting a settled rejection. Do not null cachedSvid on stream error; keep serving it and let the existing validity-window check at lines 68-71 fail closed once it actually expires. Treat an invalid or not-yet-valid response as a skipped message (continue) rather than a stream-killing throw at line 111. Keep the permanent-failure path only for close().

Unreadable-secret probe collapses every non-denial ClientError into a false "no key" refusal

consensus proposal

Codex challenge: support

The non-denial ClientError branch returns False, and pointer() converts False into a missing-key problem. That conflates an unsuccessful read with verified key absence. However, specific AWS error examples and complete CLI behavior remain untested, and error_code() is not supplied. The proposed automatic continuation is not necessary to fix the misleading diagnostic: operational errors could instead remain blocking with an accurate message. The acceptance requirement that CLI render exit 0 also depends on other preparation steps succeeding.

Claude response: support

Supported on the diagnostic defect, which is provable from the snapshot alone and does not depend on any particular AWS error code existing: any ClientError whose code is not in _DENIED reaches `return False` (sources.py:151), and pointer() reads False as proof of absence and emits a hard problem (sources.py:128), which drives REFUSED in the render/drift path (cli.py:257). The asymmetry the claim rests on is explicit in the text: BotoCoreError on the same get_secret_value call maps to None (sources.py:153) and so only warns. Two qualifications. First, the remedy is a policy choice the snapshot does not settle: returning None so the binding is kept is reasonable, but so is refusing with a message that says the read failed rather than that the key is missing; the finding should be scoped to the misleading diagnostic, not to mandatory continuation. Second, the acceptance criterion that CLI render exits 0 under a throttling stub bakes in that policy and also depends on contract check, live() and render() succeeding, none of which are supplied. Narrow acceptance to the resolve() layer: a stubbed client raising a non-denial ClientError must not produce a problem whose message claims the key is absent.

Kimi independent peer: support

The diagnostic defect is fully visible in the snapshot: any ClientError with code not in _DENIED falls through to `return False` (sources.py:151), while BotoCoreError on the same call returns None (sources.py:153). pointer() converts False into the assertion `the secret behind this pointer has no key {json_key}` (sources.py:128), which populates Resolution.problems and drives REFUSED in render/drift (cli.py:257). This conflates unreadable secrets with verified key absence. Two qualifications: (1) the remedy is a policy choice not settled by the snapshot-keeping refusal with an accurate read-failure message is equally valid, so the finding should be scoped to the misleading diagnostic, not mandatory continuation; (2) the acceptance criterion requiring CLI render exit 0 under throttling overreaches by embedding policy and depending on unsupplied contract/render/aws modules. Narrow acceptance to resolve() layer: a non-denial ClientError must not produce a problem claiming the key is absent.

Research claim and proposal

In sources.py, _has_json_key distinguishes only two AWS failure classes: error codes in _DENIED return None (treated as "cannot confirm", binding kept with a warning), and BotoCoreError returns None. Every other ClientError returns False (sources.py:151). The caller treats False as proof of absence and emits a hard problem, "the secret behind this pointer has no key <k>" (sources.py:128), which makes resolve() report problems and the CLI return REFUSED (cli.py:257). So a throttling error, a KMS decryption failure, a secret pending deletion, or an InvalidRequest on get_secret_value all become a confident, wrong statement about the secret's contents and block a deploy, while a network-level failure of the same call only warns. The asymmetry is in the code itself: BotoCoreError is explicitly mapped to None one line below the blanket False.

Make _has_json_key return False only when the secret was actually read and the key is absent. Narrow the False branch to the codes that genuinely mean "readable but not there" (ResourceNotFoundException for the secret id, and the existing json/dict checks), and return None for every other ClientError so the caller warns and keeps the binding, consistent with the BotoCoreError branch. If a distinct third state is wanted, return an enum rather than bool | None so the "could not determine" case cannot be silently confused with "absent". Consider making the warning text name the failure class so an operator can tell throttling from permissions.

unresolved

Claude response: support

Supported on mechanism, at reduced severity. server.py:280 hashes json.dumps(raw) of the parsed object with default separators and ensure_ascii, and core.py:326 stores that as artifact_sha256; json.loads preserves key order into a dict and json.dumps without sort_keys preserves it, so the digest varies across submissions differing only in key order. core.py:207 shows canonical hashing was the deliberate choice for evidence, so the lab path is inconsistent with the module's own convention, and the exported value at core.py:393 sits under a technical-evidence heading whose limits line calls it an imported artifact. Scope the fix to canonical serialization plus a precise export label; priority 1-2, not 3.

Kimi independent peer: support

The core mechanism is correct: server.py:280 passes json.dumps(raw).encode() with default settings (no sort_keys, default separators, ensure_ascii=True), and core.py:326 hashes that re-serialization. Since json.loads preserves key order and json.dumps without sort_keys preserves it, artifact_sha256 varies with input key order. This is inconsistent with core.py:207 where canonicalization with sort_keys and compact separators is deliberate. The export at core.py:393 labels this as 'Imported record SHA-256' under a 'Linked technical evidence' heading, implying verifiability that is not robustly reproducible. However, I dispute two sub-claims: (1) 'cannot equal any file the submitter holds' is false-a file containing that exact serialization would match; (2) 'MAX_BYTES guard measures re-encoded object rather than submitted payload' is technically true at core.py:286 but irrelevant because server.py:226 already bounds the raw request body. The finding should be scoped to reproducibility inconsistency and labeling, not integrity bypass or missing size guard. Priority 2, not 3.

Research claim and proposal

import_lab() receives its "artifact" as json.dumps(raw) of the already-parsed request object (server.py:280) and hashes it directly (core.py:326). Python preserves JSON input key order, and json.dumps defaults to ", "/": " separators and ensure_ascii escaping, so artifact_sha256 varies with incoming key order and does not equal the digest of any file the submitter holds. The exported report publishes this value as "Imported record SHA-256" (core.py:393) in a section headed as technical evidence, implying a verifiable binding that does not exist. This is inconsistent with assess(), which canonicalizes evidence with sort_keys=True and compact separators before hashing (core.py:207), showing the canonical form was deliberate there. The MAX_BYTES guard (core.py:286) also measures the re-encoded object rather than the submitted payload, so it is not a faithful bound on what was received.

Make the digest reproducible and honestly labelled. Minimal change: at the call site pass json.dumps(raw, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode() so it matches the canonical form already used in assess(), and change the export label to name what was hashed, e.g. "Canonical lab JSON SHA-256". Stronger option: have /api/import-lab retain the raw request body bytes and hash the submitted bytes for the lab document, so the value can be recomputed by the submitter from their own file. Either way, enforce the size bound on the submitted payload before re-encoding (do_POST already bounds the whole body via Content-Length; apply or document that bound instead of measuring the re-encoded object).
